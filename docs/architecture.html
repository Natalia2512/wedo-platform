Read me: what this document is

This is the system-level design of We DO: which parts exist, what each one does, where it runs, how the parts exchange data, and why it is built this way. Zengqi's database design, the EPW/KPI methods and the GUI all fit inside it. The architecture is frozen at the PDR; the GUI is then designed on top of it, as the professor asked at the SRR.

How to use it. Every number that depends on something not yet known (number of places, dataset size, simulation time…) comes from the Assumptions panel on the left. When a teammate gives you the real value, type it in: the sizing, the budgets and the tables update. Then save it permanently in the list at the end of the file, or click Export values and share the file.

Structure: context → drivers (the requirements that shape the design) → decisions with motivations → building blocks → traceability to the requirements → interfaces → deployment on real machines → main flows → sizing → performance budgets → test evidence → what is still to confirm.

1 · System context

We DO sits between public climate datasets and three kinds of people. It never receives private data from them: the building model stays on the expert's own computer.

Expert user
architect, engineer, researcher: explores KPIs, downloads EPW files, simulates own building locally
Public visitor
student or passer-by at the kiosk, may continue on the phone via QR
We DO team (operator)
runs the data pipeline and publishes data releases
We DOclimate data → EPW files, climate and building KPIs → map, kiosk, phone
Climate data providers
Copernicus CDS (ERA5, ERA5-Land, CORDEX), CMCC DDS (2.2 km Italy), ESGF
OLGYAY
supervisor's server at PoliTo: storage and batch computing
EnergyPlus
installed on the expert's PC; used for the kiosk precompute on OLGYAY

Inside the system boundary: pipeline, results store, API, web apps, kiosk app, local runner. Outside: data providers, OLGYAY hardware, EnergyPlus itself, the users' devices.

Boundary with the database design (Zengqi)

The architecture fixes what the API must be able to answer: all places' values for one KPI, decade and scenario; all KPIs of one place; the yearly series of one KPI for one place; the building comparison for one place; the path of one EPW. Zengqi's schema decides how the database stores and indexes this. If the schema changes, the API and the GUI do not.

university corridor

8 · Main flows

F1 · Data release (team, batch)

  1. C1 downloads the datasets onto OLGYAY (once, ≈ TB; days to weeks)
  2. C2 processes and checks them; C3 corrects model bias and writes the validation report
  3. C4 builds EPW files; C5 computes the KPIs; C6 runs the reference building for the kiosk
  4. C7 checks completeness, tags the release (e.g. v1.0) and copies it to the public server ( GB)
  5. C8/C9 switch to the new release in one step, so users never see half-loaded data

F2 · Expert session

  1. Open the site: the app and the map geometry load ( MB)
  2. Choose KPI, decade, scenario: the map recolours (budget ≤ s; prototype ≈ ms)
  3. Click a place: KPI panel and trend chart
  4. Download the EPW ( MB) or run the local runner, which downloads it itself
  5. The runner simulates cases on the expert PC (≈ min) and writes a results file
  6. The expert opens the results file in the browser: it is read locally, never uploaded

F3 · Kiosk visit

  1. Touch to start; choose a place on the map or a city button
  2. Answer the prediction question(s)
  3. See today vs future for 3–4 simple KPIs, with a scenario toggle
  4. See the reference building, no action vs adaptation (precomputed by C6)
  5. Scan the QR: the phone opens the mobile view of the same place (C14)
  6. After s without touches the kiosk resets

Glossary

APIThe fixed set of requests the apps can make to the server (the "data contract").
BatchComputed in advance in one big run, not when a user asks.
Data releaseA complete, versioned set of published results (e.g. v1.0).
EPWEnergyPlus Weather file: one year of hourly weather.
PCAPProjected capacitive touch: the touch technology of smartphones.
p9595 % of requests are faster than this value.
Read-only serverThe public server only serves results; it never computes or receives user files.
VMVirtual machine: a server rented or provided by the university.
